Sleep Guard

helper · app · VM command

Click anywhere on this card to open its code and instructions on GitHub.

What it does

Sleep Guard protects the Googlebook from losing power when the charger is unplugged or plugged in while the lid is closed and the laptop is in deep sleep. Closing the lid still puts the laptop into normal deep sleep, so battery life is not affected.

It has three parts. A small helper runs on GooglebookOS with the same permissions as adb, without root. The Sleep Guard app starts and repairs that helper automatically after every reboot, app update and Wi-Fi reconnect, and it shows the helper's status. A command in the Linux Terminal, sleep-guard, handles pairing, installing, status and logs. Once it is set up, I never have to touch it.

Problem

I would open the lid and find a black screen. Pressing a key started a full boot instead of showing the lock screen, so any open work was lost. It happened after the laptop had slept on the charger and the charger was unplugged before the lid was opened, although not every unplug caused it.

A bug report and the firmware logs showed that the embedded controller (EC), the chip that manages power, had cold-rebooted itself and cut all power while the laptop was in deep sleep (S0ix). Its reset flags read "sysjump | hard". The EC source code shows that "hard" means software ordered a cold reboot, because a crash, a watchdog reset or a power failure leaves different flags. The EC log had also recorded a "sleep hang" after an earlier charger change.

The trigger is a race. With the lid closed, GooglebookOS force-disables every wakelock, so when a charger change wakes the laptop, it falls back into deep sleep within about 60 milliseconds while the USB-C controller is still handling the change. Lenovo's EC module is closed source, so the exact sender of the reboot command could not be identified. Many other causes were checked and ruled out, including the Setup Wizard's auto-shutdown, the lid settings, an Android shutdown, the battery level, heat, the 80% charge limit and the EC watchdog.

Solution

Sleep Guard gives the hardware a moment to finish before the laptop goes back to sleep. It notices every wake that happens with the lid closed within about 5 milliseconds and checks again 15 milliseconds later that the lid really is closed. Then it briefly tells GooglebookOS that the lid is open for power purposes, which makes wakelocks work again, while it keeps the screen and the glow bar off. The hold lasts 0.3 seconds, and it stretches to a 20-second settle period when the charger has changed. After that, everything is released and normal deep sleep resumes.

It was proven live on October 10, 2026. An unplug during deep sleep was caught 87 milliseconds after the wake, a plug-in was caught 18 milliseconds after the wake, and the laptop stayed up overnight.

Safety was treated as seriously as the fix. An early version once stalled the power service for about two minutes, so the helper now reads system service output asynchronously with a deadline and a size cap. Every command has a time limit, and a watchdog releases everything and exits if the helper ever stalls. After every exit, it restores the real lid state. On a new GooglebookOS build, it runs a self-test and stands down with a notification if anything has changed, instead of guessing. It also notices when Wireless debugging moves to a new port after a Wi-Fi drop and publishes the new port, so the app can always reconnect.

Sleep Guard wins a timing race. It is not a firmware fix. Opening the lid before unplugging the charger is always completely safe.

Shadow Trackpad Fix

input helper · app · diagnostic

Click anywhere on this card to open its code and instructions on GitHub.

What it does

Shadow Trackpad Fix makes the Googlebook's trackpad work properly inside the Shadow PC cloud computer app. Two-finger scrolling becomes smooth and precise, including slow scrolling, sideways scrolling and flicks with momentum. Pinch to zoom works, three- and four-finger swipes switch windows and go back and forward, and one-, two- and three-finger taps give left, right and middle clicks.

The project has four parts. A small helper runs on GooglebookOS with adb permissions and switches itself on only while Shadow has captured the pointer. The Shadow Trackpad Fix app restarts that helper after every reboot and update, and it tells me when Shadow or GooglebookOS has been updated. A command in the Linux Terminal, shadow-trackpad, controls the helper and includes a doctor that re-checks everything after an update. Trackpad Probe is the diagnostic app that proved the root cause, and it is now the test target for the helper and the doctor.

Problem

In Shadow PC, slow two-finger scrolling did nothing, and normal scrolling was jerky and lost much of its movement. Pinch, flick and multi-finger swipes did not work at all. Turning on Shadow's Accessibility option did not help, because Shadow's Accessibility service only handles the keyboard.

Two things combine to cause it. Shadow captures the pointer with Android's older pointer capture call, and on this GooglebookOS build, which is based on Android 17, that call now gets "relative" capture mode by default. In relative mode, Android passes on only cursor moves, clicks and scrolling. Pinch, flicks and three- and four-finger swipes are dropped, and the raw finger data that Shadow's own gesture code needs never arrives. The scrolling that does arrive comes in small fractional steps, and Shadow rounds each step down to a whole number, so every step smaller than one notch becomes zero.

Trackpad Probe proved this. It captures the pointer exactly the way Shadow does and logs every event. With capture on, 100% of slow scrolls and 30% to 85% of normal scrolls were lost, and pinch, flick and swipe produced nothing. The trackpad hardware, my settings, the network and system load were all ruled out, and the system flag behind relative mode cannot be changed without root.

Solution

While Shadow holds pointer capture, the helper takes exclusive control of the trackpad, reads the raw finger data itself and runs its own gesture engine. It sends cursor moves and clicks straight to Shadow. Scrolling is sent as a synthetic two-finger touchpad drag, which Shadow's own gesture code turns into fine-grained Windows scrolling. Pinch is sent as Ctrl plus that drag, which is how Windows precision touchpads zoom. GooglebookOS intercepts the Windows key and Alt+Tab, so three-finger swipes use the Ctrl+Alt+Tab switcher instead, and four-finger swipes send Back and Forward. The moment capture ends, the trackpad goes back to Android.

It is fast. In an A/B test, the time from finger to app was 9.4 milliseconds with the helper and 11.2 milliseconds with Android's own handling, with no lost movement.

It was built to be safe and to keep working. A watchdog releases the trackpad if the helper stalls for 1.5 seconds. The app proves it is talking to the real adb service before it hands over any secret, and that secret is derived from the paired key, so only the Linux Terminal and the app can compute it. After an update, the doctor decompiles the new Shadow app, re-checks every assumption the helper relies on, and switches any broken feature to a safe fallback until the check passes again. Before release, the code went through three rounds of independent review by AI code reviewers, and a fuzz test ran one million gesture sequences with zero stuck keys or buttons. The final doctor run passed all 25 checks.

The real fix belongs in Shadow itself, which could keep the fractional scroll steps or request absolute capture mode.

Buds LE Link

helper app · plugin fix

Click anywhere on this card to open its code and instructions on GitHub.

What it does

Buds LE Link keeps Samsung's Galaxy Buds4 fully connected to Samsung's Galaxy Wearable app on the Googlebook, so the earbuds' controls, settings and battery widget work without tapping Connect over and over. It is a small background app. It reconnects the earbuds' control link a few seconds after they connect, then checks the link about once a minute for several minutes and warns me only if five of those checks fail in a row. Every 15 minutes, it also sends the reconnect signal again while the earbuds are connected. A status window shows the link state and has a Reconnect now button.

The project also includes the fix that stopped Galaxy Wearable from crashing in the first place.

Problem

The first problem was a crash. Galaxy Wearable crashed the moment the Buds4 were connected and then on every launch, and the Buds widget never appeared. Galaxy Wearable itself was fine. Its Galaxy Buds plugin was the part that crashed, because Samsung's x86-64 build of that plugin includes only 3 of its 8 native libraries, so it failed at startup.

The second problem appeared once the crash was fixed. The plugin's screens and widget showed "disconnected" while music was playing through the earbuds, and I had to tap Connect every time. The link also dropped at random.

The Googlebook connects the Buds4 over LE Audio only and turns down the older Bluetooth audio connections. The plugin reconnects automatically only when one of those older connections comes up, which never happens on this laptop. It does see the LE Audio connection, but it ignores it unless the earbuds are one specific other Galaxy Buds model and the host has a Samsung-only system feature, so the Buds4 fail that check. The plugin's control channel also closes whenever an earbud's link blips, and nothing reopens it.

Solution

The crash was fixed by reinstalling the same Play Store copy of the plugin in its ARM version, which contains all of its libraries. GooglebookOS translates it to run on the Intel processor. The plugin kept its data and its Play Store link, and it received the Nearby devices permission it had never been given. The widget then appeared by itself.

To solve the connection problem, the plugin's code was studied to find out what makes it connect. At startup, it sends itself an internal "ready" signal, and its handler for that signal does count LE Audio as connected. Any app is allowed to send that signal. Buds LE Link sends it twice, a few seconds after the earbuds connect. The first signal refreshes the plugin's stale state, and the second one opens the control channel. Audio stays on LE Audio the whole time. In the first test, the link came back about 4 seconds after the earbuds came out of the case.

I wanted it to be foolproof, so version 2 added the 15-minute check, the status window, and self-checks for every permission and battery setting it needs, with a Fix button for each one in the status window. Version 2.2 turned that window into a normal one that closes cleanly. Both fixes depend on how this exact version of Samsung's plugin behaves, so a Samsung update could undo them, and the app warns me if a different plugin version is installed.

Gmail Web App Notification Issue

notification system

Click anywhere on this card to open its code and instructions on GitHub.

What it does

This project gives the Gmail web app on the Googlebook real, lasting notifications, even when Gmail is completely closed. Each new email pops up as its own notification, stays in the Notification Center until I deal with it, and is grouped by account. Every email notification has three buttons: Reply, Delete and Mark as read. Tapping a notification opens that email in the Gmail web app.

It has four parts. A 2021 version of Google's Gmail Go app works only as the engine that receives Google's push messages. Notification Keeper turns each of its alerts into a proper notification. A helper inside Notification Keeper carries out a tap, Reply or Delete in the Gmail web app window. A small background service in the Linux Terminal handles Mark as read without opening any window.

Problem

On the Googlebook, Gmail is a web app. Its alerts are created by the open Gmail web page, and Gmail's own web code withdraws each alert about 7 seconds after posting it, so nothing is left in the Notification Center. When the window is closed, GooglebookOS ends the page within a fraction of a second. From then on nothing can notify at all, because Gmail's web code has no way to receive push messages while it is closed. Do Not Disturb, notification settings, battery settings and rate limits were all checked and ruled out.

Installing the full Gmail Android app did not solve it. On a Googlebook, the full app detects the desktop and switches itself into the same web mode, and it disables 84 of its own components, including the one that receives push messages and the one that syncs mail. The adb shell is not allowed to switch those components back on. The newer 2022 version of Gmail Go never asks for permission to post notifications, so Android blocks all of them.

Solution

The 2021 version of Gmail Go has no web mode, keeps its own push receiver and mail sync, and targets an Android version old enough that its notification permission can be granted from adb. Google's own signed copy of it was installed, granted that permission, exempted from battery limits and set to stay silent. When new mail arrives, Google's push wakes Gmail Go even if it has been closed, and it syncs the email. Notification Keeper then posts its own pop-up copy and removes Gmail Go's original. The whole chain takes about 1 to 1.5 seconds from Google's push to the pop-up. If the Gmail web app is open and posts its own alert as well, the Keeper removes that duplicate.

Tap, Reply and Delete open the right account's inbox in the Gmail web app. The helper finds the email by its exact subject and arrival time, and then it opens the email or uses Gmail's own menu to reply or delete. It only touches the screen when Gmail is the active window and nothing covers it. For Reply and Delete, it removes the notification only after the action succeeds. Mark as read works without opening anything. The background service in the Linux Terminal keeps a hidden browser signed in to each Gmail account, finds the unread email by sender address, subject and time, and clicks Gmail's own Mark as read button. Each one takes about 4 to 6 seconds. A settings guard saves my Gmail notification settings and puts them back if they are ever reset.

Every part was proven on October 12, 2026, including notifications with Gmail Go closed, Mark as read on more than one account, and tap, Reply and Delete. Archive was left out because Android shows at most three buttons on a notification. Mark as read currently needs the Linux Terminal running with Wireless debugging, and it works for @gmail.com and @googlemail.com accounts only.

Notification Keeper

open-source app

Click anywhere on this card to open its code and instructions on GitHub.

What it does

Notification Keeper is an open-source Android app that keeps web app notifications in the GooglebookOS Notification Center. When a Chrome web app or website withdraws one of its own notifications a few seconds after posting it, the Keeper posts a quiet copy that stays until I tap it or clear it. Tapping the copy opens the site or web app. The Keeper has no internet permission, does no polling and stores no message content.

It was built first for the Gmail web app. For Gmail, it goes further. It turns each email alert into a rich notification with Reply, Delete and Mark as read, it guards Gmail's notification settings, and it runs the Gmail helper described in the card above. Its long-term goal is to preserve notifications for every Chrome web app on GooglebookOS, and other developers will need to extend the code to get there.

Problem

Websites and Chrome web apps can withdraw their own notifications a few seconds after posting them, and the Gmail web app does this with every alert. The alert pops up, disappears, and leaves nothing behind in the Notification Center, so a notification that arrives while I am away from the screen is simply gone.

No GooglebookOS setting causes this. Do Not Disturb, snoozing, notification timeouts and rate limits were all checked and ruled out. The site's own code withdraws the alert, and Chrome passes that on to the system.

Solution

The Keeper is a notification listener. It recognizes notifications that Chrome delivers for websites and web apps, and it watches for the moment one is withdrawn by the app itself. It ignores notifications that I swipe away or tap. When an alert is withdrawn, the Keeper posts a copy with the same title, text and icon on its own "Kept web notifications" category, which keeps it in the Notification Center. It keeps up to 15 copies, because Android allows each app only 50 notifications. A Run test button posts a fake web notification and withdraws it after 7 seconds, so anyone can check that the Keeper catches it.

This generic keeping already works for any web app's withdrawn alerts without any changes. The rich features are the action buttons, the settings guard, and a privileged link that lets the Keeper manage another app's notification categories. Those are written only for Gmail and Gmail Go. Bringing them to other web apps means editing the app names written into the code and writing matching logic for each app, and that is the work this project invites other developers to do.

The Keeper cannot make a closed web app notify. For Gmail, that part is handled by Gmail Go, as the card above explains.

Battery Widget

system fix · repair command

Click anywhere on this card to open its code and instructions on GitHub.

What it does

This fix makes Google's built-in Batteries widget on the Googlebook show the battery level of connected Bluetooth earbuds, such as the Galaxy Buds4 and the Pixel Buds 2a, next to the laptop's own battery. It is a one-time permission change. A small command in the Linux Terminal, fix-battery-widget, re-applies it in seconds if the widget ever goes blank again, for example after a factory reset.

Problem

The earbuds showed up in Bluetooth Settings, but the Batteries widget only ever showed the laptop. The earbuds and the Bluetooth system were working normally, and the widget was even being told every time a Bluetooth device connected or disconnected. It simply could not read them.

The widget belongs to a preinstalled Google app called Settings Services. Since Android 12, an app that wants to list connected Bluetooth devices and read their battery levels needs the Nearby devices permission (BLUETOOTH_CONNECT). Settings Services asks for that permission, but on the Googlebook it had never been granted for my account, so the widget could not see any devices. Bluetooth Settings still showed the earbuds because it runs with its own system privileges.

Solution

The Nearby devices permission was granted to Settings Services over adb from the Linux Terminal. The widget refreshes when a Bluetooth device connects, and it only lists devices that are connected at that moment. When I reconnected the earbuds, both the Galaxy Buds4 and the Pixel Buds 2a appeared in the widget right away.

To make the fix stick, the permission was marked as my own choice, so the system treats it as a deliberate setting. Android's automatic removal of permissions from unused apps was also turned off for Settings Services. The fix-battery-widget command repeats all of these steps and prints the result, so I can see that it worked.

Waydroid

Linux VM · Android container

Click anywhere on this card to open its code and instructions on GitHub.

What it does

This project runs Waydroid, a complete Android 13 system with Google Play, inside the Googlebook's Linux Terminal. Waydroid includes Intel's ARM translator, so it can install Android apps that only come in ARM versions, including 32-bit ARM apps that GooglebookOS itself cannot run. Two buttons on the panel of the Linux Terminal's display open Waydroid and restart it, and the same actions are available as the terminal commands waydroid-open and waydroid-restart.

Problem

I wanted to run ARM-only Google Play apps on the x86 Googlebook. GooglebookOS can already translate 64-bit ARM apps, but it has no support for 32-bit ARM apps. Waydroid had been installed in the Linux Terminal, but Android never finished starting.

The cause was Waydroid's network setup. Its script adds an iptables rule that needs a kernel feature called the CHECKSUM target, and the Linux Terminal's kernel is built without it. The network script failed, and Waydroid gave up before Android could boot.

Three more problems appeared after that. Waydroid froze Android whenever its window was hidden, which also stopped Play Store downloads. The virtual machine's memory and swap filled up, so Android looked frozen. Google Play also refused to sign in until the device was registered with Google, because a Waydroid system is not a certified device.

Solution

Waydroid's network script was switched to nftables, which the kernel fully supports, and Android then booted in about 18 seconds with working internet and Google Play. A systemd drop-in re-applies that change every time Waydroid starts, so package upgrades cannot undo it. The unused LXC network service, which failed in the same way, was turned off.

Auto-freeze was switched off, so Android keeps running in the background. A 4 GB swap file was added at a lower priority than the fast compressed swap, which freed enough memory for the Play Store to run smoothly. I registered the device with Google so I could sign in to Google Play, and the two launcher buttons were added and tested.

An app that ships only with 64-bit ARM libraries installed successfully from Waydroid's Play Store, but no ARM app has been launched and tested yet. The virtual machine has no GPU acceleration, so Android draws everything in software. Waydroid's window appears only inside the Linux Terminal's display view, and apps with strict integrity checks usually refuse to run.

Continue On

workaround · mirroring app

Click anywhere on this card to open its code and instructions on GitHub.

What it does

This workaround brings my Android devices onto the Googlebook's screen when Google's Continue On feature is not available for them. It uses Scrcpy for Android, an open-source scrcpy client by Miuzarte that runs on GooglebookOS itself. It streams a device's screen and sound into a window on the Googlebook, and the Googlebook's trackpad, mouse and keyboard control the device directly. Nothing is installed on the phone or tablet, and no root is needed.

Problem

Continue On is part of Google's Better Together features, and it lets a Googlebook pick up apps from a phone. Google's requirements say the phone must run Android 17 or newer. The feature also launched for Pixel phones only, with Samsung support promised later. My Lenovo Tab P12 runs Android 15 and my Galaxy S23 Ultra runs Android 16, so both devices are left out.

Setting up a replacement had its own obstacles. Android 17's new local network permission had not been granted to the app. The app could not discover the devices on the network, so they had to be added by hand. The tablet refused the first connection and had to be paired again. The first stream also lagged, because the tablet was sending its full 2944 by 1840 resolution over Wi-Fi.

Solution

Before the app was installed, its download was checked against the checksum published on GitHub and its signature was verified. It was given the local network and notification permissions, allowed to run in the background and exempted from battery saving, so the connection does not drop when the app is not in front. Each device was paired once over Wireless debugging and added by the IP address and port shown on its Wireless debugging screen. The stream was limited to 1920 pixels at 60 frames per second, which removed the lag and made the stream much smoother.

The app mirrors one device at a time in a single window, and it streams the device instead of handing apps over the way Continue On does. After a device restarts, its Wireless debugging port changes, so the saved entry needs the new port. Apps that block screen capture show a black screen.

Forge IDE

AI coding IDE · app · GPU engine

Click anywhere on this card to open its code and instructions on GitHub.

What it does

Forge is my Cursor-style AI coding IDE for the Googlebook. It runs my local Llama 3.1 model through Ollama in the Linux Terminal and gives me what I have in Cursor: an editor with code intelligence next to a chat with several tabs, an agent that reads, edits and runs code for me with my approval, a visible thinking process, every change highlighted inline with Keep and Undo, checkpoints I can restore, context from files, folders, docs, past chats, the web and linter errors, attachments of any kind, voice input, memories, rules, hooks and custom modes, a Python debugger, Jupyter notebooks, a codebase index that searches by meaning, Android, Kotlin, Java and Rust development with code intelligence, virtual Android devices from Android 11 to Android 17 (phones, foldables, tablets, watch-sized screens and TVs, running in the Linux VM without an emulator), source control, a terminal, and native app windows, one per project. A GPU engine built into the app runs the same model on the laptop's Intel graphics, and I can paste screenshots, which a vision model reads for Llama. I can watch the two models work together in the chat, step by step. Nothing I type leaves the machine.

Problem

Ollama runs Llama 3.1 8B in the Linux Terminal, but a terminal is a poor place to do real coding work with a model. The CPU in the Linux VM processes prompts at only 10 to 23 tokens per second, so an agent with a few thousand tokens of context waited minutes before its first word. The VM has 7.8 GB and the model takes 5.2 GB of it, and the laptop takes memory back from the VM when it needs it; one reload into a full VM made the laptop kill the whole VM.

The Intel graphics could not help: the Terminal app only passes the GPU through to the VM on devices where Google has set a flag, the Googlebook is not one of them, and flipping the flag needs root.

Solution

A pure Python server in the VM serves the IDE (built on the Monaco editor from VS Code) and runs the agent with a tool protocol an 8B model follows reliably, checkpoints for every change, automatic syntax checks after every edit, and a prompt cache strategy that makes follow-ups answer in seconds. Memory guards show the VM's free RAM, refuse to load the model into a full VM and unload it before the VM gets into danger. Helpers such as the language servers, the debugger, notebook kernels and the small embedding model start only when needed and only when a memory check passes, and they stop again when they are not used.

For the GPU, I cross-compiled llama.cpp's Vulkan backend for Android and packaged it into the Forge app, where the Intel graphics are reachable. The app downloads the weights once from Ollama's store, asks the VM to hand memory back, and serves the model to the IDE. Prompt processing went from 10 to 23 tokens per second to about 100, the first token of a cold agent prompt from 134 seconds to 9, and a three-step agent task from 257 seconds to 50, with no model memory left inside the VM.

Also solved

Smaller fixes

These are one-off diagnoses and fixes on the same Googlebook, written up for reference.

Terminal "Keep Awake"
I thought the Linux Terminal's Keep Awake setting was broken, because the screen still went to sleep while the Terminal was open. Decompiling the Terminal app showed that Keep Awake is not a screen setting at all. It holds a partial wake lock, which keeps the processor and the Linux virtual machine running while the screen is off, and it only takes that lock after I switch away from the Terminal or the screen turns off. It does nothing while the Terminal is in front, and when its timer runs out, it switches itself back to Off. The screen was turning off because of the normal five-minute GooglebookOS screen timeout, which can be changed in the Screen timeout option of the Display settings. Later work on Sleep Guard also found that closing the lid disables every wake lock, so Keep Awake cannot keep the virtual machine running while the lid is closed. The setting works as designed, and nothing needed to be fixed.
Terminal session protection (tmux)
Long jobs in the Linux Terminal, including Claude Code, were dying in the middle of their work. The Googlebook's logs showed why. About two minutes after the Terminal app went into the background, its connection to the Linux virtual machine sometimes dropped, and the terminal server inside the virtual machine then closed the shell and every program running in it, even though the app and the virtual machine kept running. The fix was to install tmux, which keeps programs running in a session that does not depend on the window. The shell's startup file now opens or re-attaches that session automatically whenever the Terminal opens a new window, so after a dropped connection, everything is still running exactly where it was left. Command shells that programs start in the background are not affected, and setting NO_AUTO_TMUX=1 skips the feature. In testing, a simulated disconnect left the running program alive, and a new window re-attached the same session. tmux cannot help if the whole virtual machine stops, for example after a restart or when an update closes the Terminal app. Because mouse mode is on, text is selected by holding Shift while dragging.
